So far the browser compiled and ran your C for you. From this module on, much of your work runs on your own machine: you build with a real compiler, step through a crash in a debugger, let the sanitizers find memory bugs and let `make` rebuild only what changed. This lesson installs those tools once. You need five things:

- a **C compiler** (`cc`: gcc or clang),
- a **debugger** (gdb on Linux and WSL, lldb on a Mac),
- **make**,
- the **memory tools** (the sanitizers that come with the compiler, plus Valgrind on Linux or `leaks` on a Mac),
- **Node**, because every project zip is checked by `check.mjs`, a small JavaScript program.

Node runs only the checker. Your programs are plain C, built by the compiler and run as native processes.

## macOS

Open Terminal and run:

```sh
xcode-select --install
```

The Command Line Tools give you **Apple clang** (`cc` and `clang` are Apple's clang), **lldb**, **make 3.81** and **`leaks`**. Then install the current **Node LTS** with the macOS installer from nodejs.org.

A Mac with an Apple chip is **arm64**. If Terminal is set to "Open using Rosetta", or you installed an x64 Node, your tools report `x86_64` instead, and programs you build may be Intel code. The doctor you run below flags that and says how to fix it.

When you first use lldb, macOS may ask once to allow debugging.

## Windows: WSL

The course runs on Linux inside Windows, through **WSL**. In PowerShell (as administrator) run the command below, restart, and open **Ubuntu** from the Start menu:

```sh
wsl --install -d Ubuntu-24.04
```

Then, in the Ubuntu terminal, install the compiler, debugger, make, Valgrind and two helpers:

```sh
sudo apt update
sudo apt install build-essential gdb valgrind unzip curl nodejs
```

`nodejs` from Ubuntu 24.04 is Node 18, which `check.mjs` accepts. Node 18 is past end of life, so any newer LTS works too, for example the one from nodejs.org.

## Linux

On Ubuntu or Debian, run the same `apt` line in a terminal. Other distributions name the packages differently: you want gcc, make, gdb, Valgrind, unzip, curl and Node 18 or newer.

## Where your files live in WSL

WSL has its own Linux file system. Keep your course work in your Linux home folder, `~`, not under `/mnt/c` (your Windows drive as Linux sees it): builds there are slow, and file permissions and line endings can go wrong.

Your browser saves downloads on the Windows side. Copy each zip into your home folder and unzip it there:

```sh
cp /mnt/c/Users/<you>/Downloads/<name>.zip ~
cd ~
unzip <name>.zip
```

Replace `<you>` with your Windows user name and `<name>` with the zip's name. To see your Linux files in Windows Explorer, run `explorer.exe .` in that folder.

## Line endings

Windows tools often save text with **CRLF** line endings (carriage return plus newline). Linux expects just a newline. A Makefile or shell script saved with CRLF breaks: `make` and the shell read the stray carriage return as part of the command, and the errors look baffling.

So edit your course files from inside Linux. **VS Code** with the **WSL** extension does that: run `code .` in an Ubuntu terminal and VS Code edits the Linux files directly. Its status bar shows `LF` or `CRLF` for the open file, and clicking it switches.

## Your editor

Any editor works. The course suggests **VS Code** with the **clangd** extension, which shows errors and warnings as you type. **CodeLLDB** is an optional extension for debugging inside the editor; Module 3 uses the debugger from the terminal.

clangd needs to know how you build. Without that, it analyses your files with different flags from the build, so the editor's warnings don't match the compiler's. It reads them from a `compile_flags.txt` file, one flag per line. Every Module 3 zip ships this one, with the flags `check.mjs` builds with:

```text
-std=c17
-Wall
-Wextra
-pedantic
```

## The doctor

Now check the installation. Download the zip below and unzip it in your home folder (in WSL, copy it in first). In that folder, run:

```sh
node check.mjs --doctor
```

The doctor prints your architecture (and any Rosetta mismatch), your operating system, compiler and Node versions, which debuggers and memory tools it found, the `sizeof` table from a program it compiles, your cache-line and page size, and which "my machine" value to choose below. A missing compiler or too old a Node is an error, with the fix. A missing debugger or memory tool is a note.

Then run `make test` for the exercise itself, and paste each code it prints.
