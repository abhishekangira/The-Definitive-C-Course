You've read a few compiler messages already. Every clang diagnostic has the same anatomy:

`main.c:6:20: error: use of undeclared identifier 'cuont'; did you mean 'count'?`

- **file:line:column**: exactly where the compiler noticed the problem (not always where you made it).
- **severity**: `error` stops the build. `warning` lets it continue, but in this course every warning is treated as a bug. `note` adds context to the message above it.
- **message**: often with a suggestion. Below it, a **caret** `^` points at the column, and sometimes a **fix-it** shows replacement text.

**Fix the first error first.** One mistake can confuse the parser so badly that it reports errors on perfectly good lines below. Fix the first message, recompile, and see what's left. Usually the cascade disappears.

A warning doesn't stop compilation. Does a program with a warning even run? Predict before you press Run.

```c id=warning-still-runs expect=warning predict=outcome
#include <stdio.h>

int main(void) {
    int unused = 42;
    printf("still runs\n");
    return 0;
}
```

It runs: warnings are advice, and the compiler still produces a program. Many teams compile with `-Werror` so warnings fail the build, because each one is a likely bug. This course's checks do the same.

"Compiling" is really four stages, and knowing which stage complains tells you what kind of mistake you made:

1. **Preprocess**: paste `#include`s, expand macros (you saw this in lesson 1).
2. **Compile**: check types and syntax, then translate C into assembly. Most errors you've seen come from here.
3. **Assemble**: turn assembly into machine code, an **object file**.
4. **Link**: combine object files and libraries, and connect each call to the function's actual code.

**What you know now:** read `file:line:col`, fix the first error first, treat warnings as bugs, and use the stage that complains (compiler or linker) to know what kind of mistake you made. That's Module 1. Next, the problem set and the Mario project put it all together, then the checkpoint.
