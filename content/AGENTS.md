# content/: lessons, exercises, projects and quizzes

Notes for anyone editing course content. The root `AGENTS.md` comes first: its non-negotiables decide what a lesson may say and ask. The lint rules are in `tools/content-lint/README.md` and the exercise checks in `tools/exercises/README.md`. To add an exercise, follow the `add-exercise` skill (`.agents/skills/add-exercise/SKILL.md`).

## Format
```
content/modules/m01-c-in-your-browser/
  module.yaml                  id number title why hours weeks time{…} lessons problemSet project coreExercises resources retrieval
  lessons/NN-name.mdx          frontmatter: id (m01-l1), title, minutes (25–60), summary
  exercises/<id>/              exercise.yaml  starter.c  solution.c  cases.yaml  tests.json   (+ variants/<n>/ as standalone folders)
  project/<id>/                project.mdx  exercise.yaml  cases.yaml  check.json  Makefile  README.md  starter/  solution/
  quizzes/retrieval.yaml, quizzes/checkpoint.yaml
```
- **Lessons** are MDX. `tools/mdx/remark-course.ts` turns ```` ```c ```` fences into `<CodeSample>` (needs `id=`) or `<CodeBlock>` (`fragment`) and groups content into gated `<Card>`s, each ending in one interaction. Components available without imports: `Choice`, `CompilerError`, `MemoryDiagram`, `Stepper`, `NumberDrill`, `NumberPlayground`, `PipelineExplorer`, `Exercise`, `Analogy` (`js`, `c`, `breaksDown`), `Callout`, `Animation`, `YouTube`, `TestExample`, `Transcript` (below), `PlatformPicker` (the "my machine" select of Settings; neutral, so its card still ends in an interaction: lesson 3.1).
- **Fence meta keys:** `id`, `fragment` (or `fragment=partial`), `predict` (`output|outcome|choice|none`), `choices="a|b|c"`, `stdin`, `args`, `expect` (`success|warning|compile-error|runtime-error|ub|exit:N`), `expect.<gcc|clang|wasm|apple|msvc>`, `warn=-Wflag` and `warn.<compiler>=`, `platform`, `predict64`, `match` (`exact` or `close`), `reason`, `target=native`, `stdout=tty|pipe|both`, `posix`, `guardrail`, `sanitize=off`, `trace`, `timeout`, `norm`, `files`, `run`.
- **Nested drill samples** inside `CompilerError`, `MemoryDiagram`, `Stepper` and `PipelineExplorer` use `predict=none` and no 64-bit question: these components consume the fence as data and never render its prediction widget. The perfect-lesson count uses this metadata; `lint:content` enforces this as `nested-predict`.
- **`<PipelineExplorer>` tabs.** With no props it shows exactly the three tabs lesson 1.1 uses (source, `-E`, `-S`). The optional `stages="source,E,S,objdump-t,objdump-d,nm,link"` adds the live wasm32 views: `objdump-t`/`objdump-d` are `clang -c` then `objdump -t`/`objdump -d -l` of `main.o`, `nm` lists its symbols, and `link` shows wasm-ld's real result (the `size` table of `main.wasm` on success; the linker's message, with its temporary object as `<tmpN>`, on failure). `session="<id>"` adds the stored native panes: the named session's steps labelled `as: asm` (its `-S -g` listing), `as: nm` and `as: objdump` (its `-d -l` listing), one platform tab per stored run, "No stored run" for a platform in the session's `platforms` without one, and the "my machine" setting picks the default tab. Selecting a source line highlights the instructions its line info maps to, and selecting an instruction selects its source line; only instruction lines map (labels and directives stay unselected); that needs the fence to be the session's own `main.c` (apart from the final newline), or the pane says the source is different and turns highlighting off. The fixture's `pipeline` session (m97) is the test data.
- **Exercises:** `kind` is `ct` (write), `fb` (fix a bug from a symptom), `pa` (Parsons) or `lt` (runs on the learner's machine). Exactly three hints (nudge → concept → partial code). A variant inherits nothing from its parent. `tests.json` is `{version, sources, warnings, tests[{name, run{stdin,args}, expect{stdout,exit}, hint}]}`. For single-file stdin/args/stdout/exit exercises it is **generated**: write `cases.yaml` (`cases: [{name, stdin?, args?, hint?}]`, plus `memory: true` for a native memory check) and run `npm run exercises:expect` (see `tools/exercises/README.md`); never type an expectation. Hand-written unit/make tests remain hand-written. How the app gates an LT exercise's solution and variant is in `src/progress/AGENTS.md`.
- **Native sessions** (`docs/adr/0005-native-sessions.md`) show real terminal output from tools the browser can't run (linker, sanitizers, Valgrind, `make`, gdb, lldb): a folder `modules/<mNN>/sessions/<id>/` with `session.yaml` (`steps: {all, linux, macos}`, each step `run`, optional `as`, `stdin`, `exit: ok|fail|any`, `only: gcc|clang`) and the files the steps use. Session ids are unique across the course. `npm run verify` runs each one twice on Linux with gcc and with clang 22 and stores `src/generated/sessions/<module>.json`; macOS comes from the Targets workflow. Fixture examples: `tools/verify/fixtures/content/modules/m97-sessions/sessions/`. Show them in a lesson with `<Transcript session="id" step={2} />` (no `step`: every step; `beside="id2" besideStep={2}`: a second session next to it, for gdb and lldb). `step` counts in each platform's own list: `all` steps, then its group, minus the other compiler's `only` steps. It has one tab per platform (a plain label when only one platform stored the step), says "No stored run" only for a platform the session has steps for (the file's `platforms`; usually macOS before the Targets run), names a one-compiler Linux session ("gdb runs on the gcc 13 build only") instead of calling the other missing, marks the normaliser's placeholders, and keeps long lines intact: the output box scrolls sideways and takes keyboard focus. To ask about a report, use `<CompilerError session="id" step={2} stage="run" fix="ubsan" question options answer explain />` (no fence; `step` defaults to the last step). It asks which line (the report's first frame in the session's own `.c`/`.h` files, never typed; give the session `bug: main.c:5` in `session.yaml` and `verify` checks every Linux report points there), what is wrong (`options`/`answer`), and which stage failed (`stage`: `preprocess`, `compile`, `assemble`, `link` or `run`; `link` asks no line, and lint checks the stored report at that `step` is a linker's). Each question is scored for perfect lessons, first answer only: a wrong line, option or stage on the first Check stays wrong after a retry (`stage="link"` asks no line, so it scores two questions, not three). remark-course gives the exercise a stable `ceid` (the nested sample id, or `session:<id>`; the same exercise twice gets `-2`) and the `?frontmatter` loader emits the same `<instance>:<kind>` ids for `lessonPredictionStats`; `tools/mdx/lesson-qids.test.ts` checks the compiled ids against the loader's. A nested-fence CompilerError is scored the same way. Fixes ("Show a fixed version", the browser fix check) are not scored. `fix` says how the browser checks a fix: `"compile"` (a plain compile error), `"ubsan"` (the guardrail UBSan runtime), `"leak"` (leakcheck); anything else (ASan, Valgrind uninitialised values, a link error, several `.c` files) is `fix={false}`, and the next LT carries the fix. A checked fix nests one ```` ```c id=… predict=none ```` fence, the fixed program (for "Show a fixed version" and the e2e click-through). The learner sees the session's source exactly as committed, so **never comment the bug line** (`/* never freed */` is the answer): put explanations in the lesson text; `verify` rejects a comment on the `bug:` line. Never type tool output into a fence: a `text`, `console` or `sh` fence (or `bash`, `shell`, `txt`, untagged) with a tool-output marker is the lint error `hand-typed-output`.
- **Quiz items:** `predict`, `outcome`, `choice`, `ce`, `md`, `sp`, `exercise`, `np`, `order`. A `choice` with `code` has no `answer` (the verified output must equal one choice). A `ce` needs `answer`; with `session: <id>` (and optional `step`, `stage`) it shows that session's stored report instead of `code`. An `md` needs `sample`, `line`, `items` and `meta: trace predict=none`; an `sp` needs `sample` and `line` and asks two numbered parts, both read from the trace: the line one gdb `step` later, and the call stack after it (`bt`) out of three (after `step`, before it, after `next`), so `line` must call a function (lint checks the three stacks differ). An `order` with `session: <id>` sorts that session's commands: its steps must be exactly `items` on every platform (lint `quiz-order`), and the stored run is the key. That session must not run the same command twice (lint `quiz-order`: two equal lines have two right orders), and every command should read as something a learner would type for that job: no harness steps such as `sleep 1` (a timestamp workaround) in a session made for ordering. Checkpoints run in assessment mode: no hints, no solutions, explicit skip counts as wrong, one `transfer: true` item.

## Conventions
- **C standard and POSIX.** C17 + the standard library. POSIX only in M11 (`dlopen`), M13 and the capstone's provided `memlib`. POSIX samples start with `#define _POSIX_C_SOURCE 200809L` (add `_DEFAULT_SOURCE` for glibc `d_type`, `_DARWIN_C_SOURCE` for macOS `MAP_ANON`) and mark the fence `posix`.
- **`learnc.h`** (`src/runtime/c/`) is the course helper (MIT, our own). Don't ship libcs50 (licensing is ambiguous). No libc `rand()` in prediction answers; use the `learnc.h` PRNG.
- **Normalisation.** In samples only `%p` output is normalised to `<addrN>` (sessions hide the work dir and temp paths in every step, and PIDs, addresses and build ids only in steps with `as:`; see the ADR). On those lines `0`, `0x0` and `(nil)` mean NULL.
- **Traces** come from x86-64 Linux gdb and are labelled as such. Variables whose declaration has not run are recorded as `declared: false` with a placeholder value, never the stack bytes.
- **A module being built is a draft.** Keep `available: false` in `content/course.yaml` until its release PR: the app does not open it, `lint:content` reports what it still lacks as notes (`tools/content-lint/README.md`), and `module.yaml` lists only lessons that exist (a listed lesson with no file is an error). Open it at `<site>/?preview=mNN` (the Pages URL or the `npm run dev` address); run its click-through with `E2E_MODULE=mNN npm run e2e`. Exercise folder names are global across modules, so a new module prefixes them (`m03-gdb-hunt`); `duplicate-exercise` is a lint error.
- **Unit-test harness:** `#define main learner_main` plus `#include` of the file defining `main`, with `-Wreturn-type` and `-Wmissing-prototypes` silenced. Never trust its return value. Multi-file projects are tested through `make` targets in `check.json`.
- **Project Makefiles must work with GNU make 3.81**, the `make` of macOS 14, where the `project-runner` job runs them (see `.github/AGENTS.md`).

## Pitfalls
- **Compiler output quoted in prose comes from the generated data, not memory.** Lesson 6 once showed `did you mean 'count'?` for the typo `cuont`; clang 22 offers no suggestion there (it does for `cont`), so the lesson contradicted the diagnostics panel. Copy messages from `src/generated/samples` (`raw`), and re-read the sentences around them whenever a sample changes.
- **A `scan` exercise must also reject ways to hide code from the scan:** digraphs and trigraphs (`%:` is a `#`), backslash-newline, a second definition of the function, and casts in the body (see `src/testing/scan.ts`). `unit` tests trust `@@PASS` lines on stdout, so such a file also rejects `@`, `__attribute__` and `exit`-style calls (issue #42 comment; a harness token would fix it properly). Read "Operator-restricted exercises" in `tools/exercises/README.md` (`exclusive`) before writing one.
