# src/tutor/: the optional AI tutor (bring your own key)

Design in PLAN.md §2.6; the owner's decision to build it is PLAN.md §12, item 10. The tutor's progress field (`tutorAsks`) follows the schema rules in `src/progress/AGENTS.md`, and untrusted-input rules for saved settings are in `src/AGENTS.md`. `e2e/tutor.spec.ts` stubs the provider. The lesson chat (last bullet) has `e2e/lesson-chat.spec.ts`.

- **AI tutor.** The learner's API key, base URL, model choice and the provider host they have agreed to send requests to live in `tdcc:v1:tutor`, outside the progress document, so export, import and "Reset all progress" leave it alone (same idea as `tdcc:v1:playground`). The key is never logged and never put in a URL (not in the userinfo, query, path or host). Saved JSON is untrusted: wrong types are dropped, and the base URL must be `https`, or `http` on exactly localhost, `127.0.0.1` or `::1` (not a lookalike host), with no username, password or key-like query name (`key`, `token`, `secret`, `sk`, `auth`, `bearer`, and the same words joined by `.`, `_` or `-`). Consent is per host and per use: `consentedHost` (exercises) and `lessonConsentedHost` (the lesson chat); an exercise notice records the first, the lesson notice the second, the Settings notice (it names both) both, so consent saved before the lesson chat does not reach it. Clearing or replacing the key, or changing the host, clears both. The site sets no Content-Security-Policy; that URL check is the egress rule, and a request must use `tutorChatUrl` and must not follow a redirect. Nothing is sent until the learner accepts a notice that names the host (Test connection uses the same notice and does not show the model's text). After a failed substantive check, lessons and problem sets show Ask the tutor on browser ct, fb and pa exercises only. Checkpoints, retrieval quizzes (`allowTutor` false), variants, local tasks and `project/` ids do not. The prompt includes the real failing output and only the hints already opened; the reference solution is marked never reveal. A reply that repeats a solution line the learner does not already have, including one disguised by comments, case, markdown or lookalike characters, or a code block longer than three lines, is replaced with a refusal that points at the next hint. A fragment the learner can already read (their code, the statement, the shown outputs, the opened hints, a Parsons bank: `learnerVisibleText`) is not a leak, nor is a parenthesised fragment whose inside is readable; the whole-line check is never relaxed (live replies that only quoted the learner's own code were refused 6 times in 22 before this, 0 in 44 after). The comparison also folds Cyrillic and Greek lookalikes to Latin, strips every default-ignorable character and typographic quote, reads the reply as MiniMarkdown renders it, scans comments string-aware and string-blind, and refuses a bidi override. A Parsons reply that lists four or more unplaced bank lines in solution order or in reverse is refused. A red team found each of these; each has a test that fails without it. The guard stops code-form leaks only: prose that states the fix (10 of 22 live replies did) is a prompt matter, and renamed or reordered code needs a judge. The reply is rendered with MiniMarkdown, never as HTML. Answered questions are counted on the exercise as `tutorAsks` (migrate, merge and the exercise round-trip keep it; a hostile count is capped). The count is not a streak submission and it does not unlock the solution. A new check clears the reply, and an answer that arrives after a newer check is dropped and not counted. The model is a choice in Settings. "Course default" (stored as an empty model, OpenRouter only) sends the owner's fixed body: `models` (`TUTOR_MODELS`), `provider` (`TUTOR_PROVIDER`: `only` groq, cerebras, google-ai-studio, nvidia, `allow_fallbacks`), `messages` (one user message: the instructions, then the exercise) and `max_tokens` (`TUTOR_MAX_TOKENS`, adjustable), and nothing else. "My own model id" sends `model`, `messages` and `max_tokens` to any host. `tutorRequestBody` decides, so OpenRouter-only fields never reach another host, and no model on another host sends nothing (`no-model`). Exercise replies are not streamed: the guard needs the whole reply before anything is shown (the lesson chat streams). `e2e/tutor.spec.ts` stubs the provider and checks both bodies.
- **Tutor chat URL.** Appending `/` to the whole base string puts the slash in the query (`/v1?x=1` + `/` becomes a query of `x=1/`), and `new URL('chat/completions', that)` then drops the last path segment and the query. A key sitting in `?q=` was stripped before the refusal check, so the client fetched a cleaned URL. `tutorChatUrl` appends on `pathname` and copies `search` back. Do not follow redirects (`redirect: 'error'`): the `Authorization` header would be forwarded to the next host.
- **Lesson chat.** Once a key is set, a lesson shows an "Ask the tutor" button and, on a highlight, an Explain / Reply toolbar (`SelectionToolbar`, pointer and touch only: a selection made or changed with Shift+arrows or Ctrl+A hides it, since it is not in tab order; the button and the chat box are the keyboard route; on a coarse pointer Enter is a new line and Send sends). The chat (`LessonChat.tsx`, mounted by `LessonPage`, keyed by lesson so a new lesson starts a new conversation, nothing saved) streams replies through `streamTutorReply` (`client.ts`: `stream: true` added to the same two bodies, server-sent events parsed by hand, a JSON reply from a provider that ignores `stream` accepted, `aborted` for the learner's Stop, idle 30 s and total 120 s timeouts, a 6,000-character cap, the key redacted from everything shown, including every frame: a tail that could be the start of the key is held back until the reply ends normally, so an error or the cap never leaves part of it on screen). Every request carries the whole conversation, because a model remembers nothing: `buildLessonMessages` (`lessonPrompt.ts`) returns a `system` message (instructions, then the lesson), then the last 12 turns, merging same-role neighbours. `TutorMessage` is `system | user | assistant`; the exercise tutor still sends one user message. The lesson text is read from the rendered page (`lessonTextFrom` in `lessonText.ts`), not the MDX, on purpose (a code editor is read from its whole document, `src/components/editorText.ts`, because CodeMirror renders only the lines near the viewport): locked parts, an unanswered quiz's `explain=` and an unrun sample's output are not on the page, so they are never sent. Transcripts are sent too: a `<details data-transcript>` is read even when closed (`<Animation>` fetches `transcript.txt`; `<YouTube>` cuts the committed excerpt at its anchors with `segmentTranscript` in `src/components/youtube-transcript.ts` and shows it only with its attribution line and the CC BY-NC-SA 4.0 notice; the About page and each excerpt's NOTE say so). `[data-exercise]` is left out of the text and of highlights (`LEFT_OUT_SELECTOR`): the exercise tutor owns those, with its leak guard. The lesson chat has no leak guard (no solution to guard); what stops it giving away the next prediction is the prompt and the page-only text. The consent notice names the lesson (`scope="lesson"`). `e2e/lesson-chat.spec.ts` stubs the provider with an SSE body; chunk-boundary cases live in `stream.test.ts`, because `route.fulfill` sends the whole body at once.
